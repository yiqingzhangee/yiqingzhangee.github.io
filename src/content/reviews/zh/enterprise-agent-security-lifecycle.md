企业智能体的风险不在于它会不会生成一段不可靠的文本，而在于这段推理是否会通过身份、数据和工具变成真实动作。只要一个模型能够读取邮件、检索知识库、调用代码执行环境、写入数据库或触发外部系统，安全对象就已经从模型输出扩展到了完整行动链。

本文的核心观点很简单：**模型负责提出候选动作；模型之外的控制面负责决定动作是否能够发生。** 这要求安全设计把身份、权限、上下文来源、工具版本、审批、审计和恢复能力放在同一条可验证的路径上。

## 1. 风险如何进入行动链

间接提示注入是最直观的例子。网页、邮件、文档、检索结果和工具返回原本只是待处理的数据，却可能被模型误解为应执行的指令。攻击者不必直接与智能体对话；只要污染可被读取的内容，就可能影响后续规划和工具调用。OWASP 指出，RAG 或微调并不能从根本上消除这类问题，后果可以延伸到未授权访问和下游执行。[1]

风险会沿着一条常见路径被放大：

> 外部内容 → 上下文 → 规划 → 工具调用 → 数据或系统副作用

![智能体行动链中的资产与信任边界](/images/reviews/agent-security/agent-security-trust-boundaries-zh.png)

*图 1：资产与信任边界沿智能体行动链展开。*

这条路径也解释了为什么只检查提示词或只过滤输出并不充分。PoisonedRAG 说明恶意文档能够持续影响检索结果；本文将长期记忆投毒视为需要独立建模和运行期监测的运营风险，OWASP 建议对保留记忆进行校验、隔离、过期控制和完整性检查。[6] 已获信任后发生变化的 MCP 工具描述则是另一类独立风险面。[8] InjecAgent 的工具集成场景也表明，外部内容会改变后续工具决策；这些实验结果不等同于生产环境发生率，但足以说明行动决策不能建立在单次、静态验收上。[2]

## 2. 用外部行动控制面约束智能体

一个可操作的原则是把“思考”和“执行”分开。模型可以提出调用某个工具的建议，但不应自行决定是否拥有该工具、是否可以访问目标数据、是否允许在当前上下文和时段执行该参数组合。

外部行动控制面至少应校验以下事实：

- **主体是谁**：每个智能体、子智能体和连接器应有独立身份、责任所有者和声明用途。OWASP 支持智能体通信认证与发送方权限执行；所有者和用途绑定是本文提出的运营模型补充。[6]
- **请求要做什么**：工具、版本、参数、目标资源和预期副作用采用结构化格式表达。
- **为什么此刻允许**：任务边界、数据敏感度、环境、时效和风险等级都进入策略判断。
- **授权是否仍有效**：高影响操作使用一次性、短期审批；参数或资源变化后重新裁决。
- **结果是否可追溯和恢复**：日志关联输入来源、规划摘要、工具版本、参数、网络去向和最终副作用。

这不是要求用某一个产品或框架实现所有控制，而是要求授权逻辑位于模型上下文之外。对于写入、删除、支付、发布和外联等高影响动作，模型只能提供候选操作；策略执行点和必要的人类批准必须独立作出确定性判断。

## 3. 生命周期的每个阶段都需要门禁

![七阶段生命周期安全门](/images/reviews/agent-security/agent-security-lifecycle-gates-zh.png)

*图 2：生命周期安全门形成反馈闭环；发生变更后，系统重新进入评测。*

智能体的攻击面会随着模型、提示词、知识库、工具、权限和依赖的变化而变化。因此，安全不应被理解为部署前的一次测试，而应是贯穿生命周期的门禁和证据链。

| 阶段 | 要回答的问题 | 最低证据 |
| --- | --- | --- |
| 需求与设计 | 场景是否低风险、可逆且有明确损失上限？ | 所有者、禁止动作、威胁模型、数据边界 |
| 构建与集成 | 每个会影响行动的组件是否可追溯？ | 模型/提示/工具/凭据/依赖版本与权限复核 |
| 测试与评估 | 正常效用与滥用路径是否同时被测试？ | 注入、越权、外泄、记忆投毒和恢复用例 |
| 部署 | 生产环境是否真正具备隔离、限额和停止能力？ | 短期凭据、审计、回滚、紧急停止演练 |
| 运行 | 是否能关联异常动作的来源、序列与后果？ | 实时观测、异常检测、降权或隔离策略 |
| 变更 | 版本、权限或工具变化后是否重新验证？ | 差异化威胁建模、回归与分阶段发布记录 |
| 退役 | 是否清理了触发器、凭据、记忆和孤儿授权？ | 撤销、数据处置和保留审计证明 |

NIST AI RMF 将 GOVERN 作为支撑 MAP、MEASURE 和 MANAGE 的跨切面功能，并要求在生命周期内迭代开展风险管理。[4] 本文的生命周期门禁是工程运营模型，而非对 NIST 条款的逐项映射。对工程团队而言，每一扇门都应留下责任人、批准版本、测试结果、风险接受和回滚条件。

## 4. 持续 TEVV：评测必须跟着系统变化

![持续 TEVV 安全闭环](/images/reviews/agent-security/agent-security-continuous-tevv-zh.png)

*图 4：持续 TEVV 将生产证据与事件回流到策略和评测中。*

TEVV（testing, evaluation, verification, and validation）应从上线前红队扩展为运行期能力。单次测试只能描述某个版本在一组攻击下的表现；工具描述、数据源、知识库写入和攻击策略都会在生产中继续变化。

一个实用的评测闭环有四层：

1. **组件层**：测试提示词、记忆、工具 schema、策略和依赖。
2. **近真实环境层**：复现生产身份、权限、数据分级和网络边界。
3. **端到端层**：执行间接注入、越权、外泄、长程组合与恢复测试。
4. **生产层**：把真实事件、未遂事件和工具供应链漂移回灌到回归集。

安全指标也不能只报告攻击成功率。系统还应衡量正常任务完成率、误拦率、人工批准负担、发现和恢复时间，以及回滚是否真正成功。否则，一个通过大量拒绝来降低攻击成功率的系统，可能在业务上不可用。NIST 的 MEASURE 指南同样提醒，度量必须结合其适用语境，不能脱离预期用途孤立解释。[9]

## 5. 自主性应由运行证据换取

最稳妥的上线策略不是一开始追求自治，而是逐级放权：

- **L1：只读观察**——读取、分析和提出建议。
- **L2：建议后批准**——生成动作，但逐项由人批准。
- **L3：护栏内执行**——在已批准的资源、额度和动作域内执行，并持续监测。
- **L4：域内自治**——仅在经过长期验证的边界内自主规划与执行。

等级提升需要同时看到业务效用、安全测试、监控覆盖、恢复演练和事件记录的证据。重大事件、关键日志缺失、供应链来源不明或无法及时恢复时，系统应自动降级到更低的自治模式。对高影响、不可逆或跨域动作，独立策略裁决和明确的人类批准应长期保留。

## 6. 落地顺序：先让行动可控

企业不必等到所有问题都被解决才开始试点，但应从目标明确、数据范围可控、动作可逆的低风险场景起步。一个最小可行的安全基线包括：

1. 建立智能体、工具、凭据和数据资产清单。
2. 为每个智能体和连接器分配独立身份与最小权限。
3. 在模型外部署策略执行点，阻止未知工具、缺失审批和参数漂移。
4. 隔离代码执行、浏览器、数据库写入与高敏感外联能力。
5. 记录从输入来源到最终副作用的完整证据链，并验证紧急停止与恢复。
6. 用持续 TEVV 和真实运行数据决定是否扩大授权。

不应假设提示注入存在完整的模型内防线；连接工具和长程任务可能把多个单独看来低风险的调用组合为高风险结果。MITRE ATLAS 提供了一个用于分类和映射对抗性 AI 技术的共同知识库。[8] 因而成熟度不应以“模型更聪明”为主线。本文提出五项递进能力：**资产可见、身份可辨、行动受策略治理、结果可恢复、风险可持续演进。** 前一项没有建立，后一项就缺少可信证据。
